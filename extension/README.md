# Ticket Radar — 搶票雷達（Chrome 擴充功能 MVP）

搶票輸的那幾秒，通常不是手速問題。這支擴充功能處理三件事：

| 真正的原因 | 對應功能 |
|---|---|
| 電腦時鐘跟售票站差 1~3 秒，你以為 12:00:00 按，其實是 11:59:58（被擋）或 12:00:02（晚了） | **校時** |
| 回流票是隨機掉的，你盯著畫面但眨眼就沒了 | **盯哨** |
| 票出現了，可是你在別的分頁 | **叫醒** |

它是**鬧鐘，不是機器人**。不自動點擊、不自動選位、不自動送出訂單——最後按下購買的永遠是你。

## 安裝

沒有建置步驟，整包就是原始碼。

1. Chrome 開 `chrome://extensions`
2. 右上角打開「開發人員模式」
3. 「載入未封裝項目」→ 選這個 `extension/` 資料夾

## 用法

在售票頁面上點擴充功能圖示，由上往下走：

1. **在這個網站啟用** — 只對你指定的網域要權限，不是全站通吃
2. **跟這個網站對時** — 算出你的電腦快了或慢了幾毫秒
3. **設定倒數** — 填開賣時間，頁面右下角會出現用「站方時間」跑的毫秒倒數
4. **選取要盯的區塊** — 按下去之後直接在頁面上點你要盯的那塊（座位圖、張數、購買按鈕都行），Esc 取消
5. **開始盯哨** — 有動靜就閃畫面、改分頁標題、響警報音、發系統通知、把分頁切到前景
6. **打開統計頁** — 累積幾次之後，就看得出這場的回流票通常幾點掉

## 先拿假的練習

`test/fake-ticket.html` 是一個假的售票頁，可以按鈕手動「掉一張回流票」，也可以讓它每 20~40 秒隨機掉。
不用去騷擾真的售票網站就能把整套流程跑一遍。

```bash
cd extension/test
python3 -m http.server 8123
# 打開 http://localhost:8123/fake-ticket.html
```

建議這樣測：選「搖滾區 A」那塊區域 → 觸發條件選「出現關鍵字」、關鍵字填 `立即購買` → 開始盯哨 →
按「10 秒後掉一張回流票」→ **把分頁切走**，看它叫不叫得醒你。

> 注意：要用 `http://localhost`，不能直接用 `file://` 開。擴充功能的網域授權不涵蓋 `file://`。

## 原理

### 校時：怎麼從「只到秒」的資訊算出毫秒

打電話問對方現在幾點，對方說「12:00:00」——但這句話在路上走了 80 毫秒，而且對方只講到秒，真正時間可能是 12:00:00.000 也可能是 12:00:00.999。

所以每一次詢問其實只給出一個**範圍**：

```
真正的伺服器時間 T ∈ [stamp, stamp + 1000)
這個時刻對應的本機時間 ∈ [送出, 收到]
=> 偏差 = T - 本機 ∈ [stamp - 收到, stamp + 1000 - 送出]
```

問七次，把七個範圍**交集**起來，區間就被夾得很窄了。取中點是估計值，區間寬度就是誤差上限——面板上的 `±XXms` 就是它。

實作在 `background.js` 的 `syncClock()`：用 `HEAD` 請求讀 `Date` 標頭，帶快取破壞參數、`cache: no-store`、`credentials: omit`（完全不碰你的登入 cookie）。

### 統計：為什麼是「每小時幾次」而不是「總共幾次」

假設紀錄長這樣：

| 時段 | 掉票次數 | 你實際盯了多久 |
|---|---|---|
| 21:00 | 14 次 | 14 小時 |
| 03:00 | 2 次 | 12 分鐘 |

看「次數」會得到「晚上比較好守」。但把次數除以時數之後：晚上 **1 次/小時**，
凌晨 **10 次/小時**——真正該爬起來守的是凌晨。

所以統計頁所有的圖都是「每小時幾次」。分母是**觀測時長**，靠盯哨時每分鐘一次的心跳累積，
分頁關掉就停，心跳斷超過三分鐘就切成新的一段。你沒在盯的時間不會被算進去，
統計也就不會因為「你剛好晚上比較有空」而得出錯誤的結論。

另外兩個刻意的選擇：

- **一個時段盯不到 10 分鐘就不下結論**，圖上畫成灰色細線，滑過去會告訴你「資料不夠」。
- **「平均多久掉一次」只算同一段觀測之內的間隔。** 跨越兩個晚上的那個 8 小時空檔不是回流票的節奏，是你去睡覺了。

### 盯哨：為什麼不狂刷

售票頁面本來就會自己更新（它自己有 polling 或 WebSocket）。所以我們不需要自己打對方的 API——只要用 `MutationObserver` 站在旁邊看那塊 DOM 有沒有從「無」變「有」就好。**零額外流量，網站完全感覺不到。**

比對的「快照」除了文字，還包含**那塊區域裡有幾個按不下去的東西**（`disabled` / `aria-disabled`）。按鈕從不能按變成能按，是票放出來最典型的訊號。

只有在頁面完全不會自己動的時候，才需要退而求其次開「定時重整」。這個模式有三道鎖：

- 下限 **5 秒**寫死在程式裡（`HARD_MIN_RELOAD_SEC`），UI 不開放調更低
- 每次間隔加 ±15% 隨機抖動，不會變成整齊的機器節奏
- 最多跑 **30 分鐘**就自己關掉，避免無人看管一直打人家伺服器
- 命中的當下立刻停止重整（你要開始操作了，不能把頁面洗掉）
- 游標停在輸入框時跳過這一輪（不洗掉你打到一半的資料）

## 檔案

```
manifest.json            MV3 設定。只要 optional_host_permissions，授權是你一個一個網站給的
background.js            校時、開賣前的提醒鬧鐘、通知、把分頁叫到前景、動態註冊內容腳本
content/watcher.js       頁面端：浮動面板、選取區塊、MutationObserver 盯哨、閃畫面
popup/                   設定面板
stats/                   回流票統計頁（每小時掉票率、星期分布、間隔中位數、CSV 匯出）
offscreen/               警報音（MV3 的 service worker 沒有 DOM，不能播聲音，要借這個隱藏頁面）
test/fake-ticket.html    練習用的假售票頁
```

## 紅線

這些是設計上的決定，不是「暫時還沒做」：

- 不自動點擊、不自動選位、不代填付款資料
- 不碰驗證碼、不繞過排隊系統
- 不多開帳號
- 不在背景偷偷跑——只在你自己開著的分頁上運作
- 權限一個網站一個網站給，不是 `<all_urls>`

## 已知限制

- **開賣那一刻請讓分頁保持在前景。** 背景分頁的計時器會被 Chrome 降速，倒數的最後幾秒會不準；背景時只靠系統通知（開賣前 10 分鐘、2 分鐘各一次）。
- 有些網站躲在 CDN 後面，回的 `Date` 標頭是快取的時間，校時會失準。面板上的 `±` 如果大得離譜，就別太相信那個數字。
- 選取的區塊是用 CSS 路徑記住的。網站改版之後路徑會失效，面板會顯示「找不到區塊…重試中」，重選一次就好。
- 這是 MVP，只支援「一個開賣倒數」；多場次同時追還沒做。
- 統計只存在這台電腦（`chrome.storage.local`），不會上傳，也不會跨裝置同步。保留 90 天。
